Integração do aplicativo móvel Stock4event
com a API de back-end

Relatório técnico que registra a API já em funcionamento e as alterações feitas para ligar o aplicativo móvel ao back-end, em especial o perfil de cadastro, a recuperação de senha e o módulo de logística. O cenário de demonstração do sistema usa empresas de Caruaru e região.

Caruaru
2026

#resumo#Resumo

O Stock4event é um sistema de estoque, compras e operação de quiosques. O aplicativo, escrito em React Native com Expo, conversa com uma API REST em Java 17, Spring Boot 3.4 e PostgreSQL. Antes da integração descrita aqui, produtos, quiosques, marketplace, endereços, pagamentos, notificações e o resumo financeiro já eram lidos e gravados por essa API. O cadastro não persistia a escolha entre cliente, fornecedor ou os dois papéis: a conta nascia com perfil administrativo e a empresa ficava como compradora, enquanto o aplicativo guardava a escolha apenas no aparelho. A tela de nova senha chamava uma rota que não existia. Caminhoneiros e logística usavam listas fixas na tela. Este relatório explica o que já estava pronto e o que foi acrescentado: a coluna de perfil de uso, a classificação da empresa, a rota de recuperação de senha, a entrada de empresas dos dois papéis no marketplace e os recursos de caminhoneiro e de resumo logístico. O atalho de login que não passava pela API foi removido do aplicativo.

Palavras-chave: Stock4event. API REST. Aplicativo móvel. Cadastro. Logística.

#sec1#1 Introdução

Operar estoque, compra e quiosque no Stock4event depende de duas partes que precisam concordar sobre os mesmos dados. De um lado está o aplicativo móvel. Do outro, a API que grava usuários, empresas, produtos, pedidos e pagamentos no PostgreSQL. A maior parte dessa conversa já existia. O que faltava era fazer o cadastro, a sessão e a logística obedecerem ao que as telas novas passaram a pedir.

Este relatório foi escrito a partir do código dos dois projetos, no estado de setembro de 2026. Ele separa, de propósito, o que já funcionava do que foi construído na integração. A separação evita tratar rota antiga como novidade e evita descrever como pronto um comportamento que a tela apenas simulava.

#sec11#1.1 Objetivo

O objetivo é registrar, em linguagem de quem vai manter o sistema, três resultados. O primeiro é o mapa da API que o aplicativo já usava. O segundo é a persistência do perfil escolhido na abertura da conta, junto com a troca de senha pedida pela tela correspondente. O terceiro é a substituição das listas fixas de caminhoneiro e de logística por recursos HTTP próprios, sempre ligados à empresa da pessoa logada.

#sec12#1.2 Delimitação

O texto cobre a API em Spring Boot e os pontos do aplicativo que precisaram mudar para consumi-la. Telas de produto, quiosque, sacola, endereço e pagamento já chamavam a API e não foram reescritas. Também não entra aqui o desenho visual dessas telas. O rastreio descrito na logística é o que a API calcula a partir do status gravado. Não há integração com operadora de transporte, mapa ou mensagem de e-mail.

#sec2#2 O sistema Stock4event

O Stock4event atende quem vende em quiosque e quem compra de distribuidoras. O mesmo aplicativo muda de conjunto de abas conforme o papel da conta. Cliente percorre exploração, carrinho e pedidos. Fornecedor, e também quem acumula os dois papéis, trabalha com estoque, quiosque, compras e o painel da empresa. Essa escolha de interface só é confiável se o papel vier do servidor, e não de um valor esquecido no aparelho.

#sec21#2.1 O aplicativo

O aplicativo está em React Native com Expo e TypeScript. A navegação separa o fluxo de entrada (animação, boas-vindas, escolha de papel, cadastro, login e senha esquecida) do fluxo autenticado. Serviços em src/services concentram as chamadas HTTP. O endereço base é a porta 8081. No emulador Android o host de desenvolvimento é 10.0.2.2. No aparelho, o host sai do endereço que o Expo informa. No restante dos casos, usa-se localhost.

A sessão guarda o token, o usuário e o instante de expiração. Ao reabrir o aplicativo, a rota GET /api/usuarios/me confirma o token e devolve o usuário atual. Se a resposta falha, a sessão local é descartada.

#sec22#2.2 API

A API usa Java 17 e Spring Boot 3.4. A persistência é Spring Data JPA com Hibernate, dialeto PostgreSQL, e o esquema é atualizado na subida (ddl-auto=update). O script data.sql roda em seguida e aplica ajustes idempotentes: colunas que ainda não existem, cargas de demonstração e correções que podem ser repetidas sem duplicar linha. A senha é armazenada com BCrypt. O token de sessão é um JWT (JSON Web Token), com validade de 24 horas, definida em jwt.expiration-ms. A documentação interativa fica em /swagger.

O código segue camadas. O controller recebe HTTP e devolve JSON. O service concentra a regra. O repository fala com o banco. Entidade é o que se persiste. DTO é o que atravessa a fronteira HTTP, para não expor o hash da senha nem detalhes internos da tabela. A Figura 1 mostra essa divisão e o lugar do aplicativo.

#sec23#2.3 A ligação entre os dois

Cada tela que precisa de dado remoto chama um serviço. O serviço monta a URL, envia JSON quando há corpo e lê o campo erro quando a resposta não é de sucesso. Não há um gateway separado: o aplicativo fala direto com a API. Imagem de produto gravada em disco é devolvida como caminho e o aplicativo prefixa o mesmo host da API.

Dois conceitos de “perfil” convivem e não devem ser misturados. O perfil administrativo (perfis, hoje o registro Admin) é o papel interno da conta dentro da empresa e continua sendo atribuído no cadastro público. O perfil de uso é outra informação: cliente, fornecedor ou os dois. É ele que decide as abas. Antes da integração, só o primeiro era gravado no banco.

#sec3#3 O que já estava pronto

#sec31#3.1 Organização do código

O pacote com.stock4event.backend já reunia config, controller, dto, entity, exception, repository e service. Erros de validação e de regra de cadastro saem num JSON com a chave erro, no formato que o aplicativo já sabe mostrar. Os controllers declaram CORS aberto, o que permite o Expo Web chamar a API a partir de outra origem. No aplicativo nativo essa liberação não é exigida pelo aparelho, mas não atrapalha.

A subida da aplicação cria ou ajusta tabelas e, depois, executa data.sql. Esse script já inseria o perfil Admin, colunas de estoque e de pedido, cartões salvos e três distribuidoras de demonstração: Casa dos Vinhos, Cervejaria Caruaru e Whisky Labs, com produtos e imagens.

#sec32#3.2 Dados já persistidos

As entidades anteriores à logística cobrem o núcleo operacional. Empresa guarda nome, CNPJ, telefone, tipo, descrição e imagens. Usuário guarda nome, e-mail único, hash da senha, perfil administrativo, empresa e a flag de ativo. Produto pertence a uma empresa e tem preço, unidade, estoque, código e imagem. Barraca (o quiosque na interface) liga um evento a um responsável e a itens de estoque. Pedido, item de pedido e pagamento registram a venda. Solicitação de compra, com seus itens, é o pedido feito a uma distribuidora. Endereço de entrega, forma de pagamento salva e cartão salvo (sem o código de segurança) completam o checkout. Evento organiza as barracas.

O campo tipo da empresa já distinguia, entre outros valores, COMPRADOR e DISTRIBUIDOR. O marketplace listava somente DISTRIBUIDOR. Uma empresa cadastrada pela tela pública nascia com o valor padrão COMPRADOR e, por isso, não aparecia como fornecedora, mesmo quando a pessoa tinha se declarado fornecedora no aplicativo.

#sec34#3.4 Autenticação anterior

O login comparava o e-mail informado com o registro, exigia usuário ativo e conferia a senha com BCrypt. Em caso de acerto, a API emitia o JWT e devolvia também o usuário, já no DTO, sem o hash. O cadastro público criava a empresa, localizava o perfil Admin (ou Gestor, ou Gerente, se o nome Admin não existisse) e gravava o usuário ligado aos dois. E-mail repetido respondia 409. CNPJ repetido também.

Havia ainda, só no aplicativo, um desvio: e-mail admin e senha 1234 montavam uma sessão falsa, com token que a API não reconhece e com uma empresa inventada no cliente. Esse caminho não lia nem gravava nada no PostgreSQL. Quem testava por ele via abas de cliente e fornecedor ao mesmo tempo, sem que essa combinação existisse no banco.

#sec35#3.5 Onde a ligação ainda falhava

Três furos impediam tratar o conjunto como um sistema só. O primeiro era o perfil de uso. A tela anterior ao formulário pergunta se a pessoa é cliente, fornecedora ou as duas coisas. O formulário mudava os campos (CPF e telefone para cliente; empresa e CNPJ para fornecedor; os dois blocos quando a pessoa acumula os papéis). Na hora de enviar, porém, o corpo não levava essa escolha. A API ignoraria o campo se ele viesse, porque o DTO de cadastro não o declarava. O aplicativo então salvava a escolha no armazenamento local, indexada pelo e-mail. Trocar de aparelho, limpar os dados ou entrar numa instalação nova fazia a conta cair na interface de empresa, que é o ramo usado quando o perfil local não é “Cliente”.

O segundo furo era a senha. A tela “esqueceu a senha” envia e-mail e a nova senha para POST /api/usuarios/recuperar-senha. Essa rota não existia. A chamada terminava em erro e a senha no banco permanecia a antiga.

O terceiro furo era a logística. As telas de caminhoneiros, de cadastro e de envio estavam na navegação e no atalho da home da empresa, mas os nomes, rotas e a linha do tempo (“em trânsito”, pedido 1049, motorista Rafael) eram constantes no código da tela. Cadastrar um motorista só alterava o estado daquela visita. Ao sair e voltar, a lista fixa reaparecia.

#sec4#4 O que foi alterado

A integração não substituiu a API. Ela fechou os três furos da seção anterior e fez o marketplace enxergar fornecedor cadastrado pela própria tela. Contas antigas não foram reclassificadas: quem já estava como COMPRADOR continua comprador. O script apenas preenche perfil_uso com Fornecedor quando a coluna está vazia, para a interface não ficar sem papel.

#sec41#4.1 Perfil de uso no cadastro e no login

A tabela usuarios ganhou perfil_uso (Cliente, Fornecedor ou ClienteFornecedor) e cpf, opcional, com até 14 caracteres. O data.sql cria as colunas se elas ainda não existirem e preenche o perfil das linhas antigas. O cadastro passou a exigir, no corpo, o campo perfil. Valor ausente é tratado como Fornecedor, para não quebrar um cliente antigo da API. Valor fora da lista responde 400, com a mensagem de perfil inválido.

O mesmo cadastro define empresa.tipo a partir do perfil, conforme a Tabela 2. O perfil administrativo da linha de usuário continua sendo Admin. São colunas diferentes, com funções diferentes. O CPF informado no usuário é guardado só com dígitos. Se o documento da empresa já existir, a mensagem fala em CPF quando há 11 dígitos e em CNPJ nos demais casos. Isso cobre o cliente, que envia o CPF no lugar do CNPJ da empresa, porque a conta ainda precisa de uma empresa para o restante da API, que é toda organizada por empresaId.

A resposta de usuário, usada no cadastro, no login e em /me, passou a incluir perfilUso. Se a coluna estiver vazia numa linha antiga, a resposta assume Fornecedor. Login e recuperação de senha localizam o e-mail sem diferenciar maiúsculas de minúsculas. A rota /me continua achando a pessoa pelo identificador que está dentro do token; o que mudou nela é o conteúdo da resposta, não a forma de busca.

No aplicativo, o cadastro envia perfil junto com empresa e usuário. Depois do login, o contexto de autenticação lê perfilUso do usuário devolvido. O armazenamento local permanece apenas como reserva, para uma resposta antiga que ainda não traga o campo. O desvio admin / 1234 foi retirado: entrar no sistema exige uma conta real.

#sec42#4.2 Efeito no marketplace

Listar fornecedores, abrir o catálogo de um fornecedor, aceitar uma solicitação de compra e montar notificações de destaque usavam a lista fixa que continha só DISTRIBUIDOR. Com a Tabela 2, a pessoa que se cadastra como fornecedora já nasce nesse tipo e passa a aparecer. Quem marca os dois papéis nasce como AMBOS. Esses três pontos da API passaram a aceitar DISTRIBUIDOR e AMBOS. CLIENTE fica de fora da vitrine, porque essa conta compra e não oferece catálogo de distribuidora.

As cargas de demonstração que procuram as distribuidoras parceiras continuam filtrando DISTRIBUIDOR. Elas não foram alargadas para AMBOS, para não misturar conta recém-criada com o catálogo de vitrine que o script semeia na Casa dos Vinhos, na Cervejaria Caruaru e na Whisky Labs.

#sec43#4.3 Recuperação de senha

POST /api/usuarios/recuperar-senha recebe email e novaSenha. E-mail em branco responde 400. Senha com menos de seis caracteres responde 400. E-mail que não existe responde 404, com erro igual a “E-mail não encontrado.”. Quando o e-mail existe, a API gera um hash BCrypt novo, grava em senha_hash e responde 200 com a mensagem de senha atualizada. A tela que já existia no aplicativo não precisou de contrato novo: ela já enviava esse JSON.

A troca é imediata. Não há código enviado por e-mail nem prazo de validade do link, porque a tela pede a nova senha no próprio formulário. Quem conhece um e-mail cadastrado e alcança a API consegue definir outra senha. Esse limite está registrado na seção 5, para não ser lido como confirmação de identidade.

#sec44#4.4 Caminhoneiros e entregas

Duas tabelas novas guardam a operação de entrega da empresa logada. caminhoneiros tem empresa, nome, veículo, rota, status e data de criação. O status previsto na listagem é Em rota, Carregando, Disponível ou Atrasado. entregas_logistica pertence a um caminhoneiro e tem nome do cliente, cidade, rota, status e data de criação. O status da entrega é Em rota, Carregando ou Entregue.

GET /api/caminhoneiros?empresaId= devolve a lista da empresa, da mais recente para a mais antiga, cada item com as entregas e com a lista de nomes de cliente usada no cartão da tela. Sem empresaId, a resposta é uma lista vazia. POST /api/caminhoneiros exige empresa, nome, veículo e rota. A empresa inexistente responde 400. Se o corpo traz entrega com nome de cliente, o caminhoneiro nasce Carregando e a entrega também, com a rota do motorista. Cidade em branco vira “Local não informado”. Sem nome de cliente, o caminhoneiro nasce Disponível e sem entregas.

#sec45#4.5 Resumo mostrado na tela de logística

GET /api/logistica?empresaId= escolhe a entrega que a tela deve contar. Primeiro busca entregas da empresa cujo status não é Entregue e fica com a de maior identificador. Se não houver entrega em aberto, usa a entrega mais recente, inclusive a já concluída. Se não houver nenhuma, a resposta vem com vazio verdadeiro e a lista de etapas vazia. A tela, nesse caso, mostra “Sem entregas” em vez da linha do tempo fixa que existia antes. Empresa inexistente responde 400.

Quando há entrega, a API monta cinco etapas com horário a partir de criado_em: pedido confirmado no instante da gravação, separação 30 minutos depois, carregamento aos 65 minutos, trânsito aos 135 e entrega prevista aos 230. Quantas delas aparecem concluídas depende do status, como na Tabela 4. O número mostrado no cartão “Pedido” é o identificador da entrega, no formato # seguido do id. Não é o número de uma solicitação de compra do marketplace. O tempo “2h 15min” é o texto fixo do estado em trânsito, não um cálculo de rota.

O cadastro feito pela tela cria a entrega em Carregando. Os status Em rota, Entregue e Atrasado existem no modelo e na leitura, para a linha do tempo e para o selo da lista. Quem for operar o andamento completo precisará de uma atualização posterior, ou de gravar o status por outro cliente da API. Isso também está entre os limites da seção 5.

#sec46#4.6 Ajustes correspondentes no aplicativo

Um serviço novo, logisticaService.ts, lista caminhoneiros, cria o registro e busca o resumo. As três telas deixaram de usar vetores constantes. Elas leem user.empresa.id da sessão, recarregam ao ganhar foco e tratam lista vazia, falha de rede e ausência de empresa. O contador de motoristas ativos passou a ser o tamanho da lista devolvida, não o número 18 que estava escrito na tela. A Tabela 3 fecha o contrato acrescentado.

O cadastro público existente, POST /api/cadastro, não mudou de endereço. Mudou o corpo aceito e o efeito colateral na empresa. O login também manteve o endereço e passou a devolver perfilUso dentro de usuario.

#sec5#5 Limites desta entrega

Conta criada antes da coluna perfil_uso recebe Fornecedor na migração e mantém o tipo de empresa que já tinha. Se esse tipo for COMPRADOR, a pessoa vê a interface de empresa, mas não entra na vitrine como distribuidora. Só o cadastro novo aplica a Tabela 2.

A recuperação de senha não prova que quem envia o formulário controla a caixa de e-mail. Ela atende o desenho atual da tela, que coleta a nova senha na hora. Um fluxo com mensagem e token de uso único seria outra entrega.

A linha do tempo não observa GPS nem pedido do marketplace. Os horários são deslocamentos fixos sobre a data de criação da entrega, e o “pedido” exibido é o id dessa entrega. O status Atrasado só altera o texto quando a entrega já está Em rota; o formulário do aplicativo não grava essa transição.

As demais telas continuam como estavam. Produto, quiosque, sacola, endereço, cartão e financeiro não foram reabertos nesta integração, porque já tinham rota correspondente.

#sec6#6 Considerações finais

O aplicativo e a API já formavam um sistema na maior parte do fluxo comercial. A falha estava no que a interface decidia sozinha: o papel da conta, a senha esquecida e a logística de demonstração. Com o perfil gravado no usuário, o tipo da empresa alinhado a esse perfil e as três rotas novas, essas telas passam a ler e gravar o mesmo PostgreSQL que o restante do Stock4event.

Para ver as rotas novas, a API precisa ser reiniciada depois da atualização do código, de modo que o Hibernate crie caminhoneiros e entregas_logistica e o script preencha perfil_uso nas contas já existentes. O login de teste que não consultava o banco não faz mais parte do aplicativo.
